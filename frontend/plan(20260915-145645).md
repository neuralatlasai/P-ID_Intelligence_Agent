# P&ID Intelligence Agent — Frontend Implementation Plan

**Document type:** Frontend Architecture and Software Development Plan  
**Status:** Implementation baseline  
**Scope:** Frontend only — browser UI, TypeScript/React application, Node.js frontend runtime/gateway, and integration with the existing P&ID Intelligence backend  
**Backend implementation:** Fixed external dependency; not redesigned by this document  
**Model / agent execution:** Backend-owned; frontend SHALL NOT call OpenAI directly  
**Primary frontend language:** TypeScript  
**Frontend runtime:** Node.js + React application framework  
**Reference implementation:** Next.js App Router running on the Node.js runtime  
**Architecture style:** ISO/IEC/IEEE 42010-aligned architecture description; ISO/IEC/IEEE 12207-aligned software life-cycle plan; ISO/IEC/IEEE 29148-style requirements discipline  
**Quality model:** ISO/IEC 25010 quality characteristics with explicit usability, reliability, performance, security, maintainability, and accessibility gates  
**UI reference:** Supplied P&ID Intelligence Agent product screen is normative for information hierarchy and interaction intent  

---

## Abstract

This plan specifies the frontend implementation for the P&ID Intelligence Agent product shown in the supplied reference screen. The frontend shall provide a production-grade, responsive TypeScript user experience for multi-turn P&ID engineering conversations while connecting cleanly to the already-defined Python/OpenAI Agents SDK backend.

The frontend is deliberately **not** a second application backend. Model calls, agent orchestration, corpus access, GraphML operations, PDF/image reasoning, SQLite conversation persistence, retries, tool execution, and engineering-grounding logic remain backend responsibilities. The frontend owns only browser interaction, presentation state, session navigation, streaming presentation, accessibility, visual hierarchy, client-side lifecycle management, and a thin Node.js same-origin gateway to the backend.

A critical integration constraint is inherited from the backend architecture: the system does not invent a new P&ID model request or response schema. The frontend therefore shall consume and forward the backend's native OpenAI Responses-compatible input/output and streaming event structures. Internal React view-state objects are permitted as presentation projections, but they shall never become a second wire protocol or source of engineering truth.

The target user experience is a restrained engineering workspace: persistent product/session header, visible active-session state, conversational question/answer flow, observable tool activity without exposing hidden chain-of-thought, evidence/source panels, topology/revision summaries, confidence-status treatment that does not fabricate calibration, and a compact follow-up composer. The visual system shall remain quiet, information-dense, technically credible, and usable for long-running sessions.

# 2. Objective

The frontend shall provide the user-facing application for the P&ID Intelligence Agent while preserving the architectural boundaries already fixed by the backend plan.

The product shall allow a user to:

1. create or reopen a session;
2. enter an arbitrary engineering question;
3. submit the question to the existing backend;
4. observe the request progress through safe, high-level activity/tool events;
5. receive the answer incrementally when streaming is enabled;
6. inspect cited engineering files and evidence references;
7. inspect topology, revision, conflict, and impacted-asset findings when present;
8. understand whether evidence is strong, partial, conflicting, or insufficient without presenting fabricated probabilistic confidence;
9. ask follow-up questions in the same persisted backend session;
10. start another independent session without contaminating the active session;
11. recover gracefully from transport, timeout, cancellation, and backend failures;
12. use the interface efficiently on desktop and smaller displays.

The frontend shall reproduce the **information architecture** and **interaction intent** of the supplied product reference, not merely its color palette.

# 7. Architecture Decisions

## 7.1 ADR-FE-001 — Next.js + React + TypeScript on Node.js

Reference implementation:

```text
Next.js App Router
React
TypeScript
Node.js runtime
```

Rationale:

- one TypeScript codebase for browser and Node boundary;
- first-class server route handlers for same-origin backend proxying;
- straightforward streaming with Web Streams;
- production routing;
- static asset optimization;
- deployment simplicity;
- no need for a separate Express/Fastify service for the demo.

The plan does not depend on a specific framework version number. At implementation freeze, exact versions SHALL be pinned in the lockfile and CI matrix.

## 7.2 ADR-FE-002 — Node is a frontend gateway, not a second business backend

Node route handlers own:

```text
same-origin browser endpoint
backend URL isolation
header allowlisting
stream pass-through
request cancellation propagation
frontend-specific security headers
basic transport logging
```

Node SHALL NOT own:

```text
engineering logic
agent logic
session persistence
GraphML logic
PDF logic
model logic
tool logic
```

## 7.3 ADR-FE-003 — Browser never knows BACKEND_BASE_URL

The Python backend URL shall be server-only configuration:

```text
BACKEND_BASE_URL
```

Browser code calls only same-origin frontend routes.

Benefits:

- no browser CORS dependency;
- backend topology remains private;
- one place to apply frontend transport policy;
- no accidental direct backend coupling in components.

## 7.4 ADR-FE-004 — Native OpenAI/Agents response types remain the wire contract

The frontend shall consume the backend's native Responses-compatible output items and stream events.

The TypeScript project SHOULD use the official OpenAI TypeScript package as a **type source only** for the relevant generated Responses API unions.

The exact imports shall be verified against the pinned package during implementation.

The frontend SHALL NOT copy/paste or manually re-declare the OpenAI event union.

## 7.5 ADR-FE-005 — Presentation models are allowed only inside the UI boundary

The frontend may define internal view-state types such as:

```ts
type StreamPhase =
  | "idle"
  | "connecting"
  | "streaming"
  | "finalizing"
  | "completed"
  | "failed"
  | "cancelled";
```

and:

```ts
interface TurnViewState {
  userText: string;
  assistantText: string;
  phase: StreamPhase;
}
```

These are UI projections only.

They SHALL NOT be serialized as the backend API contract or treated as engineering truth.

## 7.6 ADR-FE-006 — Streaming path uses Fetch + ReadableStream, not EventSource

The backend streaming request is a POST with a request body.

Browser implementation therefore uses:

```text
fetch()
→ Response.body
→ ReadableStream reader
→ SSE parser
→ native event projector
```

Do not use browser `EventSource`, because it does not provide the required POST-body interaction model.

## 7.7 ADR-FE-007 — No automatic retry of streamed POST requests

A POST may have reached the backend and persisted input even when the browser loses the connection.

Therefore:

- no automatic retry after a submit;
- no silent replay after partial streaming;
- retries require explicit user action;
- GET health/items MAY use bounded read retries.

This prevents duplicate conversational turns.

## 7.8 ADR-FE-008 — Backend session state is canonical

Frontend stores only:

```text
active session ID
small local session shortcut list
draft input
UI preferences
panel expansion state
```

Conversation history is fetched from:

```text
GET /v1/sessions/{session_id}/items
```

through the Node gateway.

Local storage is convenience state, not a conversation database.

## 7.9 ADR-FE-009 — URL identifies the active session

Reference route:

```text
/s/{sessionId}
```

Benefits:

- refresh-safe;
- shareable inside the permitted environment;
- clear browser navigation semantics;
- component tree does not hide session identity in opaque global state.

## 7.10 ADR-FE-010 — Evidence rail is progressive enhancement over the canonical answer

The canonical user-visible truth is always the assistant answer text returned by the backend.

Right-side cards are presentation projections.

If section extraction fails:

```text
the complete answer remains visible
no evidence is dropped
the UI does not invent missing structure
```

## 7.11 ADR-FE-011 — Activity panel never exposes hidden chain-of-thought

The supplied reference uses a “Reasoning & tool calls” area.

The implementation may retain that product label if required, but visible content SHALL be limited to:

- high-level execution stage;
- observable tool name;
- tool started/completed/failed state;
- safe file reference;
- elapsed time;
- model/output status.

It SHALL NOT render hidden model reasoning or internal chain-of-thought.

Preferred user-facing title:

```text
Activity & tool calls
```

## 7.12 ADR-FE-012 — Numerical confidence is disabled until calibrated

The reference includes a numeric confidence visualization.

The initial frontend shall instead show:

```text
Confidence
Calibrated score unavailable
Evidence support: Supported | Partial | Conflicting | Insufficient
```

when such evidence status can be derived explicitly from the returned answer.

No radial “0.94” control appears until a calibrated metric is part of the accepted backend/product contract.

## 9.1 Submit body

The body remains:

```text
string
or
array of OpenAI TResponseInputItem-compatible objects
```

The baseline UI sends a standard OpenAI-compatible user input item representation or the backend-supported string form.

No frontend domain wrapper is added.

Rejected:

```json
{
  "question": "...",
  "sessionId": "...",
  "mode": "pid",
  "options": {}
}
```

The session ID already exists in the path.

## 9.2 Non-streaming output

The body remains:

```text
array of native OpenAI response output items
```

## 9.3 Streaming output

The body remains an SSE stream carrying native OpenAI Responses-compatible events.

The Node gateway SHALL NOT translate event names or payload shapes.

## 9.4 Session history

The history route returns native OpenAI/Agents input-item-compatible objects.

Frontend projects these into transcript rows.

## 9.5 Transport errors

The frontend preserves HTTP status meaning.

Example handling:

| Status | UI behavior |
|---|---|
| 400 | Show invalid request message; keep draft |
| 404 | Show session/resource unavailable |
| 408/504 | Show run timeout |
| 413 | Show request/file limit message |
| 422 | Show incompatible input message |
| 429 | Show service busy; allow explicit retry |
| 500 | Show internal failure with request ID if available |
| 502/503 | Show upstream/service unavailable |
| network error | Show connection failure; never auto-replay submit |

# 15. Node.js Gateway Design

Browser SHALL call Node routes, and Node SHALL forward to Python backend routes.

Reference mapping:

```text
Frontend Node                                 Python backend

GET  /api/health                       →     GET  /healthz

POST /api/sessions/:id/responses       →     POST /v1/sessions/:id/responses

POST /api/sessions/:id/responses/stream
                                           → POST /v1/sessions/:id/responses/stream

GET  /api/sessions/:id/items           →     GET  /v1/sessions/:id/items

DELETE /api/sessions/:id               →     DELETE /v1/sessions/:id
```

## 15.1 Proxy rules

Node route handler SHALL:

1. validate session ID length/character policy;
2. construct backend URL only from server configuration;
3. forward method;
4. forward body without domain transformation;
5. forward `Content-Type`;
6. forward request cancellation signal;
7. set `cache: "no-store"`;
8. preserve backend status;
9. preserve response body;
10. preserve safe correlation headers;
11. remove hop-by-hop headers;
12. never log full user/model/corpus content by default.

## 15.2 Streaming proxy

Streaming route SHALL return the upstream response body directly as a stream.

Conceptual TypeScript:

```ts
export async function POST(
  request: Request,
  context: RouteContext,
): Promise<Response> {
  const sessionId = validateSessionId(await resolveSessionId(context));
  const body = await request.text();

  const upstream = await fetch(
    `${BACKEND_BASE_URL}/v1/sessions/${encodeURIComponent(sessionId)}/responses/stream`,
    {
      method: "POST",
      headers: {
        "content-type": request.headers.get("content-type") ?? "application/json",
        "accept": "text/event-stream",
      },
      body,
      signal: request.signal,
      cache: "no-store",
    },
  );

  return new Response(upstream.body, {
    status: upstream.status,
    headers: passStreamingHeaders(upstream.headers),
  });
}
```

The upstream response body SHALL NOT be buffered before being returned.

## 15.3 Cancellation propagation

Browser `AbortController.abort()`:

```text
browser fetch cancelled
→ Node request signal closes
→ Node upstream fetch signal closes
→ Python backend observes disconnect/cancellation
→ backend releases run resources
```

# 17. SSE Client

## 17.1 Submit

The client submit flow:

```text
user presses Send
→ validate non-empty draft
→ create AbortController
→ POST same-origin stream route
→ check HTTP status before parsing
→ read response.body
→ parse SSE frames
→ JSON-decode data payload
→ project native event
→ update UI incrementally
→ on stream close, refresh backend session items
```

## 17.2 Parser requirements

SSE parser must correctly handle:

- arbitrary TCP/chunk boundaries;
- CRLF and LF;
- multiple `data:` lines;
- empty keepalive/comment frames;
- UTF-8 split across chunks;
- final frame without an extra chunk;
- malformed frame detection;
- cancellation.

Use a tested event-stream parser rather than line-splitting each network chunk manually.

## 17.3 Unknown events

Protocol is forward-evolving.

Projector behavior:

```text
known event → handle
unknown event → retain in debug diagnostics if enabled, otherwise ignore safely
```

Unknown events SHALL NOT crash the conversation.

# 18. Stream Projection

The stream projector converts native events into transient UI state.

It is not an API schema.

State machine:

```text
idle
  ↓ submit
connecting
  ↓ first valid event
streaming
  ↓ response completed / stream finalization
finalizing
  ↓ history reconciliation
completed

connecting/streaming/finalizing
  ├─ abort → cancelled
  └─ failure → failed
```

## 18.1 Text output

Only user-visible output text deltas are appended to the answer surface.

The projector SHALL NOT append:

- hidden reasoning content;
- encrypted reasoning;
- internal IDs;
- raw tool arguments into the answer.

## 18.2 Tool activity

When native events expose tool/function calls, map them into a safe activity record:

```text
tool name
state: requested / running / complete / failed when observable
safe file basename/path if intentionally visible
elapsed duration if measurable
```

If completion cannot be determined from the raw event stream, show:

```text
Requested
```

and reconcile from session history after stream completion.

## 18.3 Final reconciliation

After successful stream termination:

```text
GET /api/sessions/{sessionId}/items
```

Project backend-persisted history and reconcile the visible turn.

This guards against:

- missed final SSE frame;
- local delta assembly bugs;
- reconnect/navigation after completion;
- tool-event visibility differences.

Backend history wins.

# 57. Stream Race Conditions

The implementation must explicitly handle:

## 57.1 Double submit

Prevent while current same-session request is active.

## 57.2 Route change during stream

Abort the active browser request before navigating to another session.

## 57.3 Late event after abort

Ignore events after terminal local state.

## 57.4 History refresh before final stream event

Only reconcile after stream termination or explicit terminal error.

## 57.5 Component unmount

Abort active fetch.

## 57.6 Stale history response

Bind history fetch to current session ID and ignore a response for a prior route.

# 74. Reference Node Proxy Skeleton

The following illustrates direction and ownership only.

```ts
// src/lib/backend/proxy.ts

const BACKEND_BASE_URL = requireServerEnv("BACKEND_BASE_URL");

export async function proxyBackend(
  request: Request,
  backendPath: string,
): Promise<Response> {
  const method = request.method;
  const body =
    method === "GET" || method === "HEAD"
      ? undefined
      : await request.text();

  const upstream = await fetch(
    new URL(backendPath, BACKEND_BASE_URL),
    {
      method,
      headers: buildBackendHeaders(request.headers),
      body,
      signal: request.signal,
      cache: "no-store",
    },
  );

  return new Response(upstream.body, {
    status: upstream.status,
    headers: buildClientHeaders(upstream.headers),
  });
}
```

Route:

```ts
// POST /api/sessions/[sessionId]/responses/stream

export async function POST(
  request: Request,
  { params }: RouteContext,
) {
  const { sessionId } = await params;
  validateSessionId(sessionId);

  return proxyBackend(
    request,
    `/v1/sessions/${encodeURIComponent(sessionId)}/responses/stream`,
  );
}
```

# 75. Reference Streaming Hook Skeleton

```ts
export function useAgentStream(sessionId: string) {
  const [state, dispatch] = useReducer(runReducer, initialRunState);
  const abortRef = useRef<AbortController | null>(null);

  async function submit(inputBody: unknown) {
    const controller = new AbortController();
    abortRef.current = controller;

    dispatch({ type: "SUBMIT", submittedText: extractVisibleUserText(inputBody) });

    try {
      const response = await fetch(
        `/api/sessions/${encodeURIComponent(sessionId)}/responses/stream`,
        {
          method: "POST",
          headers: {
            "content-type": "application/json",
            "accept": "text/event-stream",
          },
          body: JSON.stringify(inputBody),
          signal: controller.signal,
        },
      );

      if (!response.ok) {
        throw await toFrontendTransportError(response);
      }

      if (!response.body) {
        throw new Error("Streaming body unavailable");
      }

      dispatch({ type: "CONNECTED" });

      await consumeNativeResponseStream(
        response.body,
        (event) => projectNativeEvent(event, dispatch),
      );

      dispatch({ type: "RECONCILING" });
      await refreshSessionHistory(sessionId);
      dispatch({ type: "RECONCILED" });
    } catch (error) {
      if (controller.signal.aborted) {
        dispatch({ type: "CANCELLED" });
      } else {
        dispatch({ type: "FAILED", error: normalizeFrontendError(error) });
      }
    } finally {
      abortRef.current = null;
    }
  }

  function cancel() {
    abortRef.current?.abort();
  }

  return { state, submit, cancel };
}
```

Implementation details shall preserve native backend input semantics; `inputBody` is not a P&ID DTO.
